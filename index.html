Merge Files: From Brute Force to Intuition

Don't memorize the algorithm. Discover why it works.

1. Problem ko pehle samjhein

Given an array of file sizes, merge all files into one file with the minimum total computation cost. Merging files of sizes x and y costs x + y.

Rules: koi bhi do available files chuno → cost = unka sum → dono hat kar ek nayi file (size = sum) aa jaati hai → cost total mein add → jab tak ek file bachi na ho.

2. Brute force khud discover karein

Ab sabse pehla thought kya aayega? "Mujhe nahi pata ki sabse pehle kaunsi files merge karni chahiye. Toh saari possibilities try karke dekhte hain!" Neeche asli recursion chal rahi hai — har node ek real function call hai.

Code ko samjhein: base case 0 isliye return karta hai kyunki ek file bachi toh aur merge ki zaroorat nahi. j = i + 1 isliye ki pair (2,3) aur (3,2) same hai. Naya collection isliye banta hai ki original files safe rahein aur har branch alag explore ho. Merge hui do files exclude hoti hain aur unka sum insert hota hai. Recursive result mein mergeCost add karte hain kyunki total = abhi ki cost + baaki ki cost. minCost sab pairs dekhne ke baad hi sahi hota hai.
Pairs ki ginti: n(n−1)/2. Har merge ke baad n ek kam hota hai, par har state phir se saare pairs try karti hai — isliye sequences tezi se badhte hain.

4. Greedy idea — reasoning se

Ek cheez observe karein: jo file hum merge karte hain, woh aage bhi kisi aur file ke saath merge hoti hai. Toh ek file ka size future merges ki cost ko bhi affect karta hai. Files [1, 2, 10, 20] par do strategies dekhein:

Strategy A: badi files pehle

Strategy B: chhoti files pehle

66 vs 49: ek badi file jaldi merge hui toh woh baar baar cost mein judti rahi. Toh idea: har baar do sabse chhoti available files merge karein?

Ek button dabayein.
Sirf examples proof nahi hote. Proof (exchange argument) ka intuition:
Kisi bhi merge tree mein file ki cost = size × depth (kitni baar woh merges mein shamil hui). Har tree mein sabse deep level par do siblings hote hain. Maan lo optimal tree mein wahan badi files a, b hain aur chhoti files x, y upar hain. x ↔ a swap karo: change = (x−a)(da−dx) ≤ 0, kyunki x ≤ a aur a zyada deep hai. Matlab cost badhi nahi. Y ↔ b ke liye bhi wahi. Toh ek optimal tree hai jisme do smallest files deepest siblings hain — yaani unhe pehle merge karna safe hai. Merge ke baad same structure ki problem bachti hai, n−1 files ke saath, aur argument dobara lagta hai (induction).

8. Complexity

Brute force: har state saare pairs try karti hai, aur har step par n ek kam hota hai — total calls lagbhag n!(n−1)!/2n−1 jaise tezi se badhte hain (section 3 mein asli counts dekhein). Koi simple polynomial nahi.
Min Heap: n−1 merges; har merge mein 2 extractions + 1 insertion, har ek O(log n) → O(n log n). Initial build O(n) (heapify) ya O(n log n) (repeated insert). Auxiliary space O(n) heap ke liye (input/output alag).
